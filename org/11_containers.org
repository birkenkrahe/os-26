* Definitions

- *Virtualization*
  #+begin_quote
  Creating a virtual version of a computing resource (e.g., a full
  machine). A *virtual machine (VM)* simulates an entire computer
  system, including its own OS. :contentReference[oaicite:0]{index=0}
  #+end_quote

- *Containerization*
  #+begin_quote
  OS-level virtualization: packaging an application together with its
  dependencies into an isolated environment called a
  *container*. Containers share the host OS kernel but isolate user
  space.
  #+end_quote
- *Container*: An isolated runtime environment containing application
  code, libraries and dependencies.

- *Docker*: A widely used platform for building, distributing, and
  running containers.

- *Container orchestration*: Automated management of multiple
  containers: deployment, scaling, coordination.

- *Kubernetes (K8s)*: A system for orchestrating containers across
  multiple machines: groups containers into logical units (pods);
  manages distributed systems.

* Use Cases

- *Virtualization*
  - Server consolidation (run many VMs on one machine)
  - Running legacy systems
  - Isolation for testing different OS environments

  *Example:* Running a legacy Windows application on a Linux machine
  using a virtual machine (~wine~ - see [[https://www.winehq.org/][www.winehq.org/]])

- *Containerization*
  - Microservices architecture[fn:1]
  - Reproducible development environments
  - Running multiple applications on a single host reliably

  *Example:* Packaging a =Node.js= web application (with its exact =Node=
  version and dependencies) so it runs identically on a developer
  laptop and a cloud server.

- *Container orchestration*
  - Managing many containers at scale
  - Load balancing and scaling applications
  - Automating deployment pipelines

  *Example:* Automatically scaling a web service (e.g., an online store)
  from 3 to 30 containers during peak traffic using Kubernetes.

* Pros / Cons

** Virtualization (VMs)

- Advantages
  - Strong isolation (separate OS)
  - High flexibility (different OS per VM)
  - Good security boundaries

- Disadvantages
  - Heavyweight (full OS per VM)
  - Slower startup
  - Higher resource usage

** Containerization

- Advantages
  - Lightweight (shared kernel)
  - Fast startup
  - Portable and reproducible environments
  - Efficient resource usage

- Disadvantages
  - Weaker isolation than VMs
  - Same OS kernel requirement
  - Security depends on host OS

** Container Orchestration

- Advantages
  - Scales applications easily (horizontal scaling)
  - Automates deployment and recovery
  - Improves system reliability and efficiency

- Disadvantages
  - High complexity
  - Steep learning curve
  - Operational overhead

* Comparison Table

| Feature      | Virtual Machines  | Containers    | Orchestration      |
|--------------+-------------------+---------------+--------------------|
| Level        | Hardware          | OS-level      | System-level       |
| Isolation    | Strong - Full OS  | Shared kernel | Managed at scale   |
| Startup time | Slow              | Fast          | Depends on cluster |
| Resources    | High              | Low           | Optimized on nodes |
| Portability  | Moderate          | High          | High (distributed) |
| Typical tool | VirtualBox/VMware | Docker        | Kubernetes         |
| Main purpose | Run multiple OS   | Package apps  | Manage containers  |

Steps:
1. Create a folder =my-docker-app= and =cd= into it
   #+begin_example sh
   mkdir -p my-docker-app
   cd my-docker-app
   #+end_example

2. Create a simple Python script =hello.py=
   #+begin_example python
     import os

     print("Hello from inside a customer Docker container!")
     print(f"I am running on: {os.uname().sysname}")
   #+end_example

3. Create the =Dockerfile=:
   #+begin_src txt :tangle my-docker-app/Dockerfile
    # Use an official Python runtime as a parent image
    FROM python:3.9-slim
    # Set the working directory in the container
    WORKDIR /app
    # Copy the current directory contents into the container at /app
    COPY hello.py .
    # Run hello.py when the container launches
    CMD ["python", "hello.py"]
   #+end_src

4. Build the docker image: Tell Docker to read the =Dockerfile= and turn
   it into an image named =my-python-app=. The =.= at the end tells Docker
   to look for the =Dockerfile= in the current directory.
   #+begin_example sh
   docker build -t my-python-app .
   #+end_example
   Output:

   [[../img/my-python-app.png]]

5. Check that image was created with =docker images=

6. Run the new image:
   #+begin_example sh
   docker run my-python-app
   #+end_example
   Output:
   #+begin_example
   Hello from inside a customer Docker container!
   I am running on: Linux

1. Wrote code =hello.py=

* Review Questions 2

1. What is the difference between the Docker client and the Docker
   daemon?
   #+begin_quote
   The Docker client is the command-line program the user runs. The
   Docker daemon is the background service that builds, runs, and
   manages containers.
   #+end_quote

2. What does ~docker ps~ show?
   #+begin_quote
   It shows currently running containers.
   #+end_quote

3. What does ~docker ps -a~ show?
   #+begin_quote
   It shows all containers, including stopped containers.
   #+end_quote

4. What happens when you run ~docker run hello-world~?
   #+begin_quote
   Docker looks for the ~hello-world~ image, downloads it if needed,
   creates a container from it, runs it, and then the container exits.
   #+end_quote

5. What is a Docker image?
   #+begin_quote
   A Docker image is a read-only template containing files,
   dependencies, and instructions needed to create a container.
   #+end_quote

6. What is a Docker container?
   #+begin_quote
   A Docker container is a running or stopped instance created from a
   Docker image.
   #+end_quote

7. What does a Dockerfile do?
   #+begin_quote
   A Dockerfile is a recipe that tells Docker how to build an image.
   #+end_quote

8. In the Python demo, what did ~docker build -t my-python-app .~ do?
   #+begin_quote
   It built a Docker image from the Dockerfile in the current
   directory and gave it the name ~my-python-app~.
   #+end_quote

9. Why did the simple Python container stop immediately?
   #+begin_quote
   It ran the Python script, printed its message, and then the process
   ended. When the main process ends, the container stops.
   #+end_quote

10. Why did the web app container keep running?
    #+begin_quote
    It started a Flask web server, which keeps listening for requests.
    #+end_quote

11. What does ~-p 8080:5000~ mean?
    #+begin_quote
    It maps port 8080 on the host machine to port 5000 inside the
    container.
    #+end_quote

12. What does ~-d~ mean?
    #+begin_quote
    It runs the container in detached mode, meaning it runs in the
    background.
    #+end_quote

13. Why did the web app need ~host='0.0.0.0'~?
    #+begin_quote
    It tells Flask to listen on all network interfaces inside the
    container so that requests from outside the container can reach
    it.
    #+end_quote

14. Why do we remove containers during cleanup?
    #+begin_quote
    Stopped containers remain on the system until removed. Cleanup
    avoids clutter and saves disk space.
    #+end_quote

15. What is the difference between deleting a container and deleting an image?
    #+begin_quote
    Deleting a container removes one instance created from an
    image. Deleting an image removes the template used to create
    containers.
    #+end_quote

* Glossary

|---------------+-------------------------------------------------------|
| Docker        | Platform for building, running, managing containers   |
| Docker client | The ~docker~ command used at the shell                  |
| Docker daemon | Background service that performs Docker operations    |
| Docker socket | Communication endpoint used by client 2 talk 2 daemon |
| Image         | Read-only template used to create containers          |
| Container     | Running or stopped instance of an image               |
| Dockerfile    | Text file containing instructions for building image  |
| Build context | Directory sent to Docker during ~docker build~          |
| ~FROM~          | Dockerfile: specifying the base image                 |
| ~WORKDIR~       | Dockerfile: setting working directory inside image    |
| ~COPY~          | Dockerfile: copying files into the image              |
| ~RUN~           | Dockerfile: executing command while building image    |
| ~CMD~           | Default command executed when the container starts    |
| ~EXPOSE~        | Documents the port containerized app expects to use   |
| Port mapping  | Connecting host port to container port, ~8080:5000~     |
| Detached mode | Running a container in the background with ~-d~         |
| Docker Hub    | Public registry where Docker images can be downloaded |
| Registry      | Storage location for Docker images.                   |
| Tag           | Version or label for an image, e.g. ~python:3.9-slim~   |
| Base image    | Existing image used as starting point for a new image |
| Layer         | One cached filesystem change created by Dockerfile    |
| Cache         | Reused build layers that make repeated builds faster  |
| ~--no-cache~    | Build option forcing Docker to rebuild every layer    |
| Logs          | Output produced by the main process inside container  |
| Cleanup       | Removing stopped containers and unused images         |
